# Atlas Agentic Engineering OS

## Resumo

Atlas Agentic Engineering OS e o nome canonico da area completa que o Atlas
esta construindo: um sistema operacional de engenharia onde um gestor humano
expressa objetivo em linguagem natural, ambigua e incompleta, e o Atlas opera
uma organizacao de engenharia de software por IA.

Ele nao e "programacao assistida por IA". Esse termo descreve uma IA ajudando
um programador. O alvo do Atlas e maior: substituir operacionalmente uma area
tech completa por um gestor humano e uma organizacao agentica capaz de conduzir
produto, arquitetura, implementacao, infraestrutura, qualidade, seguranca,
release, observabilidade, incidentes, documentacao, cartografia e aprendizado.

Categoria de mercado:

```text
Agentic Software Engineering
```

Nome canonico no Atlas:

```text
Atlas Agentic Engineering OS
```

## Definicao Canonica

Atlas Agentic Engineering OS e o sistema que transforma intencao humana ambigua
em entrega de engenharia verificavel, operando como uma empresa de software
interna, com departamentos especializados, contratos, gates, evidencias,
certificacao e memoria organizacional.

Frase de referencia:

```text
Um gestor pede em linguagem humana; o Atlas opera a area de engenharia inteira.
```

## Papel no Atlas

Ele substitui operacionalmente a coordenacao cotidiana de uma area tech:

- Product Manager;
- Engineering Manager;
- Tech Lead;
- Software Architect;
- Backend Engineer;
- Frontend Engineer;
- Mobile/Desktop Engineer;
- DevOps/Platform Engineer;
- SRE;
- QA Engineer;
- Security Engineer;
- Code Reviewer;
- Release Manager;
- Technical Writer;
- Data/Observability Analyst;
- Knowledge Manager.

O humano continua como operador soberano: define direcao, aprova risco,
prioriza, corrige intencao e decide tradeoffs importantes. O Atlas faz a
engenharia.

## O Que Nao E

Atlas Agentic Engineering OS nao e:

- chatbot de codigo;
- IDE agentica;
- terminal com LLM;
- wrapper de Claude, Codex, Gemini ou Goose;
- agente unico autonomo;
- CI runner;
- dashboard de tickets;
- tela bonita de SDD;
- colecao de prompts;
- Forge OS isolado;
- Atlas Code isolado.

Essas pecas podem existir dentro do sistema, mas nao sao o sistema.

## Onde Se Encaixa

```text
Atlas
-> Atlas AI / Autonomous Intelligence OS
   -> Sovereign OS
   -> Epistemic OS
   -> Knowledge Governance System
   -> Agentic Engineering OS
      -> Autonomous Software Company Runtime
      -> Autonomous Engineering OS
      -> Programming Governance System
      -> Atlas Dev
      -> Atlas Forge / Forge Continuum OS
      -> Atlas Code
      -> Evidence / Certification
      -> Cartographic Knowledge OS
```

O Agentic Engineering OS e a camada organizacional. Os filhos sao runtimes,
gates, surfaces e departamentos.

## Contratos

Use estes nomes com precisao:

| Conceito | Nome correto | Uso |
|---|---|---|
| Categoria geral de mercado | Agentic Software Engineering | Area externa, comparacao, concorrentes |
| Sistema Atlas inteiro para engenharia | Atlas Agentic Engineering OS | Doc-mae, arquitetura, foco estrategico |
| Runtime executivo com departamentos | Atlas Autonomous Software Company Runtime | Coordenacao interna de departamentos |
| Loop autonomo de trabalho | Atlas Autonomous Engineering OS | Goal, world model, RAG gate, plano, repair, certificacao |
| Governanca de codigo | Atlas Programming Governance System | Placement, spec, task, evidence, cartografia |
| Fabrica pesada de software | Atlas Forge Continuum OS / Forge OS | Obras longas, multiagente, provider topology |
| Cockpit humano | Atlas Code | Interface operacional do humano |

Contratos detalhados vivem em `atlas-agentic-engineering-os-contracts.md`.

Invariantes:

- intencao ambigua precisa virar objetivo operacional;
- software enterprise precisa de produto, arquitetura, implementacao, QA,
  seguranca, release, observabilidade, documentacao e learning;
- provider executa, mas nao governa autoridade;
- surface mostra runtime e evidencia, mas nao decide a arquitetura;
- claim de pronto sem evidence e falso completo.

## Principio Central

O poder do Atlas nao vem de "usar um modelo melhor". Vem de transformar um
provider em uma organizacao de engenharia:

```text
modelo
-> contexto correto
-> spec correta
-> plano correto
-> ferramentas corretas
-> evidencias corretas
-> review correto
-> aprendizado correto
-> proxima execucao melhor
```

Por isso o objetivo no Rivals e plausivel: Atlas Dev/Forge usando Sonnet pode
competir com modelos maiores quando o processo melhora contexto, escopo,
verificacao, continuidade e aprendizado. O custo pode ser maior que Sonnet puro,
mas precisa comprar qualidade, confiabilidade e autonomia suficientes para
justificar.

## Fluxo

```text
Human ambiguous intent
-> Executive Intake
-> Product clarification
-> Risk and impact classification
-> Knowledge bootstrap
-> Codebase world model
-> Spec / design / plan / tasks
-> Department routing
-> Execution
-> QA / tests / review / security
-> Release / deployment / rollback plan
-> Observability / incident readiness
-> Evidence pack
-> Documentation / cartography update
-> Certification
-> Learning / compounding
```

Nada disso deve depender da memoria da conversa. Tudo precisa ser recuperavel
por docs canonicos, read models, receipts, evidence ledger e cartografia.

## Regras para IA

- Use "Agentic Software Engineering" para a categoria de mercado.
- Use "Atlas Agentic Engineering OS" para o sistema Atlas.
- Nao reduza o objetivo a programacao assistida por IA.
- Nao trate Atlas Code, Forge, Dev, Company Runtime ou provider como o sistema
  inteiro.
- Antes de criar departamento, leia `atlas-agentic-engineering-os-contracts.md`.
- Para codigo, obedeca `atlas-programming-governance-system.md`.
- Para trabalho pesado, obedeca `atlas-forge-continuum-os.md`.
- Para autoevolucao do Atlas, obedeca Self-Construction, Sovereign e Epistemic
  gates.

## Escopo de Implementacao

O OS cobre a organizacao inteira de engenharia, mas cobertura conceitual nao
significa runtime pronto. Toda area AAEOS deve ser lida em dois eixos:

```text
doc_maturity: DOC L0..L4
implementation_state: runtime_verified | implemented_partial | spec_only | north_star | deprecated
```

`DOC L4` significa que a documentacao esta forte. Nao significa que comando,
surface, provider topology, loop, merge, replay ou evidencia estejam operando em
producao. Para runtime atual, leia `atlas-agentic-engineering-os-implementation-reality.md`
e `atlas-agentic-engineering-os-runtime-gap-matrix.md` antes de prometer,
executar loop autonomo, declarar 100%, criar backlog ou comparar Atlas Dev/Forge
com providers externos.

Detalhes de departamentos, data model, gates e autonomy ladder vivem em
`atlas-agentic-engineering-os-contracts.md`.

## Evidencias

Evidence minima por entrega enterprise:

- goal/spec/plan/task hashes;
- provider decision receipt;
- context/code intelligence receipt;
- execution receipt;
- test result ou blocker;
- review/security finding quando aplicavel;
- release/rollback decision quando aplicavel;
- docs/cartography update ou decisao explicita;
- certification.

## Riscos

- Otimizar somente UI/chat e perder a empresa de engenharia inteira.
- Copiar concorrente externo e quebrar a arquitetura propria.
- Escrever codigo sem qualidade, seguranca, release, observabilidade ou docs.
- Exigir que o gestor humano vire gerente tecnico detalhado.
- Gastar mais que provider puro sem melhorar contexto, review e evidence.
- Deixar documentacao incompleta e desorientar futuras IAs.

## Exemplos

Pedido humano:

```text
melhora o billing, esta confuso e dando erro em alguns clientes
```

Resposta do OS: intake, discovery, spec, architecture, Dev ou Forge, tests,
review, security, release, evidence, docs, cartography e learning.

Pedido humano:

```text
crie a nova area de automacao interna
```

Resposta do OS: placement de dominio, product spec, design, task contracts,
execucao, QA, release, cartography e certification.
