# Atlas Compounding Engineering Intelligence

## Resumo

Atlas Compounding Engineering Intelligence e o patamar acima do Hyperflow.
Hyperflow faz o Atlas entender, rotear, executar, auditar e certificar uma
tarefa. Compounding Intelligence faz o Atlas ficar estruturalmente melhor depois
de cada tarefa.

O objetivo nao e memoria maior. O objetivo e vantagem composta: cada debug,
review, implementacao, pesquisa, erro, override humano, benchmark e comparacao
contra rival gera aprendizado operacional verificavel que melhora execucoes
futuras.

## Onde Se Encaixa

O sistema fica acima de Hyperflow e abaixo da governanca de self-improvement
estrutural. Ele nao substitui Router, RAG, Atlas Dev ou Atlas Forge; ele aprende
com todos eles e devolve aprendizado governado.

```text
Prompt
-> Intent Kernel
-> Router Runtime
-> Specialist Flow
-> RAG Spine
-> Execution Contract
-> Dev / Debug / Review / Research / Forge
-> Receipts + Telemetry
-> Outcome Evaluator
-> Learning Distiller
-> Compounding Memory
-> Router/RAG/Flow improvement
-> Temporal Certification
```

| Camada | Papel |
| --- | --- |
| Hyperflow | Execucao auditavel de ponta a ponta. |
| Router Runtime | Escolhe flow correto. |
| RAG Spine | Recupera contexto, codigo, memoria, docs, testes e evidencia. |
| Atlas Dev | Programa leve/medio com evidencia. |
| Atlas Forge | Executa Obras pesadas e longas. |
| Compounding Intelligence | Aprende com outcomes e melhora todo o sistema. |

## Papel no Atlas

Compounding Intelligence e a camada que transforma execucao em vantagem
acumulada. Ela observa resultados, destila aprendizados, promove memoria
operacional e alimenta Router, RAG, specialist flows, Atlas Dev e Atlas Forge.

Ela nao decide sozinha o produto, nao aplica self-modification sem gate e nao
troca evidencia por intuicao. Seu papel e fazer cada ciclo real do Atlas
melhorar os proximos ciclos com rastreabilidade.

## Fluxo

Fluxo obrigatorio:

```text
execution receipts
-> outcome evaluation
-> learning candidates
-> promote / hold / discard / benchmark / self-improvement
-> compounding memory
-> runtime consumption
-> temporal certification
```

Uma execucao so compoe inteligencia quando produz pelo menos um destes efeitos:

- memoria operacional aprovada;
- benchmark case reproduzivel;
- heuristic update governado;
- RAG feedback mensuravel;
- self-improvement queue item com evidence;
- certificacao temporal com delta.

### Certificacao O-1 da campanha Fable

Durante o sweep O-1, dois contratos viraram piso congelado:

1. O gateway generico nao pode fabricar learning signal por interacao. O check
   `gateway_does_not_fabricate_learning_signals` exige ausencia de
   `recordCompoundingFlowSignal(` em `AiGatewayService`; o caminho valido e o
   conductor alimentar `AtlasCompoundingRuntimeService::recordExecution` com
   `learning_signal` substantivo, `engineering_run_memory`, evidence refs e
   flow da tarefa.
2. Providers que mutam workspace diretamente precisam ter scope guard sobre
   alteracoes unstaged, staged/cached, todos os untracked nao ignorados e
   ignored explicitamente proibidos. Isso impede uma edicao permitida de
   mascarar arquivo novo fora de escopo, inclusive se o provider tentar
   `git add` no arquivo proibido ou criar arquivo ignorado declarado em
   `forbidden_files`.

Provas congeladas:

- `tests/Feature/Ai/AtlasCompoundingEngineeringIntelligenceTest.php`
- `tests/Unit/Ai/AtlasDecide/AtlasEngineeringRunConductorServiceTest.php`
- `tests/Unit/Ai/Programming/AtlasDev/Http/PipelineRunExecutorHermesProviderTest.php`
- `tests/Unit/Ai/Programming/AtlasDev/Http/PipelineRunExecutorTest.php`

## Regras para IA

- Nao chamar trace bruto de aprendizado.
- Nao promover memoria sem evidence refs, confidence e revalidation policy.
- Nao alterar heuristica critica sem before/after, rollback e teste.
- Nao declarar superioridade contra Claude Code/Codex com uma bateria pontual.
- Nao permitir que Router aprenda com caso sem ground truth.
- Nao deixar RAG usar feedback historico sem registrar source utility.
- Nao transformar preferencia isolada do operador em regra global.
- Nao encerrar tarefa Hyperflow relevante sem outcome receipt.

## Escopo de Implementacao

### Outcome Evaluator

Avalia a execucao finalizada e mede qualidade de flow, retrieval, execucao,
evidencia e resposta. Detecta override humano, flow errado, contexto
insuficiente, falha de gate, retrabalho e necessidade de aprendizado.

### Learning Distiller

Transforma outcomes, receipts e telemetry em candidatos limpos. Deve filtrar
ruido e extrair apenas padroes que melhoram routing, retrieval, debug, review,
Dev, Forge ou benchmark.

### Compounding Memory

Memoria operacional versionada, governada e revalidavel.

Tipos canonicos:

| Tipo | Uso |
| --- | --- |
| `intent_memory` | Prompts ambiguos. |
| `routing_memory` | Escolha de flow e fallback. |
| `retrieval_memory` | RAG, queries, ranking e context packs. |
| `codebase_memory` | Conhecimento provado do repo. |
| `debug_memory` | Padroes de erro. |
| `review_memory` | Riscos recorrentes. |
| `forge_handoff_memory` | Promocao para Obras pesadas. |
| `rival_benchmark_memory` | Onde Claude/Codex vencem, perdem ou empatam. |
| `failure_pattern_memory` | Falhas que devem virar teste, gate ou alerta. |

### Heuristic Evolution Engine

Atualiza heuristicas com evidencia. Exemplos: aumentar `atlas_debug` quando
prompt contem erro/stack trace; aumentar `atlas_forge` quando pedido pede Obra,
enterprise completo ou one-shot perfeito; exigir retrieval receipt antes de Dev
editar codigo em tarefas com incerteza.

### RAG Feedback Loop

Mede quais fontes foram uteis, quais viraram ruido, quais faltaram, quais
queries funcionaram, quais context packs ajudaram e quais docs ficaram
obsoletos.

### Benchmark Generator

Cria casos reproduziveis a partir de falhas reais: flow errado, RAG insuficiente,
handoff incompleto, derrota para rival, teste falho ou correcao humana.

### Temporal Certification

Compara snapshots por periodo, flow e rival. Deve responder se o Atlas melhorou,
piorou, empatou ou nao tem evidencia suficiente.

## Dependencias

Depende de:

- Hyperflow Runtime com receipts e telemetry;
- Router Runtime com flow decision persistida;
- RAG Spine com retrieval receipts e context pack hash;
- Atlas Dev e Forge emitindo execution receipts;
- Evidence Ledger ou persistencia equivalente;
- docs-health para governanca documental.

Nao depende de UX pesada. A implementacao deve comecar no backend, contratos,
persistencia, services, testes e certificacao.

## Evidencias

Evidencias obrigatorias para declarar pronto:

- outcome receipts persistidos;
- learning candidates com evidence refs;
- compounding memories com confidence e revalidacao;
- RAG feedback events;
- benchmark cases gerados de falhas reais;
- heuristic updates com before/after e rollback;
- temporal certification com delta por flow;
- testes unitarios/feature e docs-health verdes.

## Riscos

| Risco | Mitigacao |
| --- | --- |
| Acumular ruido | Learning Distiller com promote/hold/discard. |
| Aprender errado | Exigir ground truth, evidence e confidence. |
| RAG enviesar para arquivos populares | Medir utility, noise e missed sources. |
| Heuristica quebrar Router | Before/after, teste e rollback. |
| Claim exagerado contra rival | Claim policy baseada em bateria e incerteza. |
| Memoria velha dominar decisao | Expiry e revalidation policy. |

## Definition Of Done

Atlas Compounding Engineering Intelligence esta completo quando:

- Hyperflow nao encerra execucao relevante sem outcome receipt;
- Atlas Dev, Debug, Review, Research e Forge produzem learning signals;
- Learning Distiller separa ruido de aprendizado operacional;
- Compounding Memory influencia Router/RAG/flows com evidence e confidence;
- RAG aprende com fontes uteis, ruido e lacunas;
- benchmark generator cria casos a partir de falhas reais;
- self-improvement queue prioriza melhorias por impacto verificavel;
- temporal certification mostra evolucao por flow e rival;
- claims contra Claude Code/Codex sao automaticamente limitados pela evidencia.

## Pisos certificados — Sweep O-1 da Campanha Fable (2026-06-12)

Auditoria adversarial multi-agente (mandato de refutar, 2 verificadores independentes
por achado) certificou os pisos compounding/capture antes do merge-livre. Contratos
estruturais que NÃO podem regredir (cada um tem teste congelado):

- **Gateway nunca fabrica learning signals** — o hook `recordCompoundingFlowSignal`
  (boilerplate por interação, fonte do ~94% de noise) foi removido; o readiness exige a
  AUSÊNCIA dele e a presença do feed real (conductor → `recordExecution`).
  Prova: `AtlasCompoundingEngineeringIntelligenceTest`.
- **Memória ativa deduplica por conteúdo** — re-promover o mesmo claim/scope/type
  REVALIDA a memória existente (nunca duplica; `memory_hash` inclui candidate_hash
  único-por-run e inundava o top-5 do `approvedForFlow`).
  Prova: `AtlasCompoundingRuntimeServiceTest::test_repromoting_the_same_claim_*`.
- **Capture gate enforce não dropa learning real** — padrões de fixture divididos em
  fortes (1 hit rejeita) e fracos (vocabulário de prosa; exige 2+ co-ocorrências);
  `content_hash` canonicalizado (caixa/espaço/ordem de chaves/lista escalar).
  Prova: `AtlasCaptureQualityGateTest`.
- **Auto-apply nunca vaza aprovação forjada** — falha de apply após approve reverte o
  carimbo para a fila de revisão; G3 lê evidence_refs da coluna canônica (nunca do
  proposed_state do produtor; sample/effect zerados sem evidência canônica).
  Prova: `AtlasAutonomousLearningApplierTest`.
- **Runtime nunca auto-aplica heurística** — `apply=true` vindo de `recordExecution` é
  forçado a `proposed` para QUALQUER key (a classificação crítica por prefixo era
  controlada pelo caller). Prova: `AtlasCompoundingRuntimeServiceTest`.

Pendências roteadas (não são deste subsistema): veredito anti-Goodhart do juiz do Loop
(O-2d), persistência do contrato de acceptance para re-prova no promote (O-3),
verificação do receipt Decide + allowlist de validação Forge (O-6). Marco Zero da
campanha: Evidence Ledger `01KTWCPTNZQDQ2NGMD8G8NP83K`.
