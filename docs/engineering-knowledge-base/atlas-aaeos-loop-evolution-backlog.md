## Resumo

Este documento e o **backlog de evolucao do loop** para as duas unicas areas em escopo: o **AAEOS** (toda a area de engenharia de software — specs, tests, memory, context, dev, forge, gates, evidence, governance, surfaces) e a **Factory/loop** (o proprio loop de auto-evolucao 24h de stewardship/area-focus). Nada fora dessas duas areas entra.

Regras de leitura:

- **Executaveis primeiro, north-star no fim.** Itens `solid_runtime` (prontos) ficam de fora. So entram `partial_runtime` e `spec_runtime_gap` no conjunto executavel. Itens north-star entram marcados `is_north_star=true` e ficam dependency-gated na cauda — nunca no ready set ate que seus itens de substrato estejam entregues.
- **Real-ou-bloqueado.** Cada item foi cruzado com a Implementation Reality. Execucao e gated/review-required: o loop consome este doc pelos gates normais (Pilar 1 DECOMPOSER + atlas_dev gates).
- **Autoridade honesta.** Gap Matrix + Implementation Reality + runbook = canonical. A revisao AAEOS + docs de sugestao da factory = proposal/chat. Itens derivados de proposal sao `status=needs_operator_review` (Secao 7).
- **Dedup.** O mesmo gap em multiplas fontes vira UM item com `source_refs` mesclados (ex.: Atlas Decide upstream = S5/S15/S18 -> S19).
- **Reconciliacao code-verified 2026-05-31.** Slices cruzados com auditoria de codigo direta. Dois marcadores novos no metadata: `code_verified=solid_runtime|partial_runtime|spec_runtime_gap` (estado real no codigo) e `status=done` (code-verified solid_runtime; FORA do executable set, verify-only — o loop NAO reimplementa). Itens S49-S55 acrescentados da auditoria; todo slice novo carrega evidence_ref de linha de codigo real. Em conflito, o marcador `code_verified` vence o `status=` antigo. **Fato bloqueante:** o loop esta `autonomy_tier=0` (scan-only) com `autonomy_tier_active` hardcoded em 0 e sem caminho de promocao — por isso S49 (Onda 0) precede toda execucao; sem ele nenhum slice executavel materializa.

## 3. Como o loop consome este doc

A Secao 6 e uma tabela de slices `S1..S165` no formato exato do `BuildPlanDocumentParser` (Pilar 1). A Secao 10 codifica o DAG via setas `Sx -> Sy`. O DECOMPOSER le ambas, materializa cada slice como tarefa candidata com objetivo, aceite testavel, rota e R-level, e o atlas_dev gate executa apenas o que esta `ready`, com dependencias satisfeitas e com escopo atomico seguro.

Para a trilha L7-L10, `status=ready` significa **implementacao de codigo permitida pelo loop**, nao autorizacao para efeito soberano. Slices sensiveis como self-construction governada e promocao L7 continuam exigindo assinatura/receipt no proprio metodo e nos testes; o loop pode criar as classes e gates, mas os metodos devem retornar bloqueio honesto quando a assinatura, evidencia ou precondicao real estiver ausente.
